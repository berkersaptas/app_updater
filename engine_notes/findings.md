# Phase 1 findings

## Answers to the technical questions

1. **Artifact:** release Dart AOT code is `libapp.so`, an ELF shared object containing snapshot
   symbols. Flutter assets remain separately packaged under `assets/flutter_assets`.
2. **APK path:** `lib/<android-abi>/libapp.so`; the engine is alongside it as `libflutter.so`.
3. **Relationship:** `libflutter.so` is the runtime/engine; it loads the AOT snapshot from
   `libapp.so`. A patch must be generated by a compatible engine/Dart SDK and for the device ABI.
4. **Startup:** `FlutterActivity` obtains a `FlutterEngine`; `FlutterLoader` initializes native
   libraries and forms engine arguments; `FlutterJNI` crosses into the Android engine shell;
   `DartExecutor` launches Dart.
5. **AOT path source:** `FlutterLoader.ensureInitializationComplete` emits ordered
   `--aot-shared-library-name=` arguments using explicit inputs plus
   `FlutterApplicationInfo.aotSharedLibraryName` and `nativeLibraryDir` fallbacks.
6. **Runtime override:** yes in the locally pinned Flutter 3.44.6 embedding, provided the path is
   passed before VM initialization and survives `getSafeAotSharedLibraryName` validation.
7. **Kotlin sufficient:** yes for this narrow POC. `MainActivity.provideFlutterEngine` creates
   `FlutterEngine(context, engineArgs)`.
8. **Engine fork:** not needed for this pinned revision. Older/stable revisions without this safe
   argument handling would require an embedding/engine patch near `FlutterLoader` plus the Android
   shell's AOT library resolution; carrying that fork would be version-sensitive.
9. **Private artifact:** the embedding intentionally permits canonical `.so` paths below
   `Context.filesDir`. Actual execution still has to be verified on each target Android build and
   OEM policy.
10. **Linker constraints:** the file must be valid ELF for the device ABI, readable/mappable under
    SELinux, compatible with the packaged engine, and loadable inside the app's linker namespace.
    Android platform policy and Play dynamic-code policy are separate from technical feasibility.
11. **Fallback:** the loader rejects missing, out-of-root, non-`.so`, or hash-mismatched files before
    engine creation, marks state `failed`, and creates the engine without an override. An unconfirmed
    `pending_boot` on the next process start follows the same base fallback.

## Device proof

Verified on an arm64-v8a Android 16 device on 2026-08-14:

- The installed base APK cold-started with `Hello v1`.
- Only patched `libapp.so` was then copied to app-private storage; the APK/native shell was not
  replaced.
- After a force-stop and cold start, the UI hierarchy reported `Hello v2`.
- `patch_state.json` moved from `pending` to `active` after the first-frame MethodChannel signal.
- Logcat reported `Verified patch 1; attempting patched boot` followed by `Patch 1 is active`.
- A deliberately incorrect engine revision was rejected before AOT loading; state became `failed`,
  the precise mismatch was persisted as `failure_reason`, and the UI cold-started as `Hello v1`.
- Reinstalling the correct generated manifest restored `Hello v2` and `active` state.

This proves alternate AOT selection for the pinned engine/device combination. Other Android/OEM
linker and SELinux combinations still require compatibility testing.

The runtime contract has been separated into `ota_core`, while the Android implementation lives in
`ota_runtime_android`. The sample app now only supplies the Flutter host integration and
boot-success signal.

The automated device acceptance suite later passed the complete matrix on the same device:
compatible signed activation, tampered-signature rejection, SHA-256 mismatch, engine mismatch, Dart
mismatch, base-release mismatch, ABI mismatch, build-mode mismatch, missing artifact, and an
unconfirmed-boot rollback. It restored the device to `Hello v2` / `active` at completion.

Lifecycle retention was also verified from the device: `last_known_good=true`, quarantine was
capped at five entries after repeated failures, and one active patch artifact remained stored.

## binary_diff device proof (Phase 2E)

Verified on an arm64-v8a Android device on 2026-08-17, same acceptance style as the Phase 1 proof
above but for `artifact_kind=binary_diff` instead of `full_aot_library`:

- A real base APK and a real patched APK were built from `sample_app`'s own two entrypoints
  (`scripts/build_base.sh`, `scripts/build_patch.sh` with `OTA_ARTIFACT_KIND=binary_diff`). Both
  produced a 2,884,496-byte `libapp.so`; the generated diff was 7,128 bytes.
- After installing the base APK and staging the diff-based patch, a force-stop and relaunch showed
  `Verified binary_diff patch 1; attempting patched boot` then `Patch 1 is active` in logcat, and the
  UI showed `Hello v2`.
- A second relaunch of the same active patch did not re-invoke bspatch (cached reconstruction reused
  from `ota/patches/1/libapp.reconstructed.so`).
- A bit-flipped diff blob was rejected cleanly: `Patch.patch()` threw (`Integer overflow: 64-bit
  offsets not supported`), `BinaryDiffArtifactResolver` turned that into a `Result.failure`,
  `PatchLoader` failed and quarantined the patch without crashing, and the app booted the base APK's
  `Hello v1` normally.

This proves the `binary_diff` artifact kind end to end on real hardware: base-artifact lookup from
the installed APK, on-device bspatch reconstruction, caching, and safe fallback on corruption. See
`engine_notes/phase_2_engine_feasibility.md` for the design this implements.

## Compatibility contract

Every patch is now signed with Ed25519 and bound to the base `versionName+versionCode`, Flutter
engine revision, Dart SDK version, Android ABI, release build mode, and artifact SHA-256. Build
scripts derive toolchain values from `flutter --version --machine`; Gradle embeds them plus a
trusted public keyring and revoked key-id list in the APK, while the patch build writes signed
metadata to `patch_manifest.json`. Any signature, key-revocation, hash, or compatibility mismatch
disables the patch and selects packaged `libapp.so`.
